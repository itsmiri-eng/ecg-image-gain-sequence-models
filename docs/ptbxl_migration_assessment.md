Generated PTB-XL images are not automatically a better test of real paper ECG performance, and none of the previously claimed generated dataset was found in this workspace.** Switching datasets also requires an explicit change of label task and, if native signals are used, input modality.

## The labels are a different task

Using the local `scp_statements.csv` diagnostic mapping and all present SCP keys, without a likelihood threshold, gives these overlapping superclass counts:

| PTB-XL superclass | Records containing that label |
| --- | ---: |
| NORM | 9,514 |
| MI | 5,469 |
| STTC | 5,235 |
| CD | 4,898 |
| HYP | 2,649 |

There are 5,144 records with multiple diagnostic superclasses and 411 with none of these mapped diagnostic labels. The natural five-superclass task is therefore **multilabel**, rather than the current mutually exclusive `Normal`, `MI`, `Abnormal`, `History_MI` task. A fresh protocol must define the confidence policy, handling of unmapped records, training objective and evaluation measures. Five sigmoid outputs with a multilabel loss and per-label metrics are a possible implementation; they would not be a directly comparable four-class experiment.

PTB-XL does not provide a `History_MI` diagnostic superclass matching the Mendeley folder. The manuscript proposed deriving active-versus-history labels from infarction-stage annotations, then imposing a class-priority and one-record-per-patient selection rule. That is an additional derived-label policy, not the original five-superclass benchmark and not a verified equivalence to Mendeley labels. Locally, `infarction_stadium1` is blank for 16,187 records and `unknown` for another 3,430; `infarction_stadium2` is blank for 21,696. These whole-dataset counts demonstrate limited stage coverage, not a clinical interpretation of any individual ECG. Reusing the historical mapping would need explicit validation and a saved source-record manifest.

## CPU feasibility and representation choices

The existing `/opt/anaconda3/bin/python` environment already has **WFDB 4.3.1**, NumPy, PyTorch and Matplotlib. No installation was needed. Four records, including the previously flagged constant-V5 record `12722`, were read through `wfdb.rdsamp`. Each decoded to finite values with shape **1,000 time samples × 12 leads**, sampling rate 100 Hz and units mV; each selected header and data file matched the shipped checksum. The known constant V5 channel was reproduced and recorded, not silently excluded.

These four local reads took approximately 1.6–4.7 ms per ECG in this run. This establishes decoding feasibility, not a training-speed benchmark. No forward pass, training epoch or large cache was performed.

| Representation | Per-record float32 signal/input size | Practical implication |
| --- | ---: | --- |
| Native 100-Hz waveform, 12 × 1,000 | 48,000 bytes | Direct temporal sequence for a small 1D CNN–LSTM; avoids image rendering and trace extraction. |
| Native 500-Hz waveform, 12 × 5,000 | 240,000 bytes | Five times the signal payload and input sequence length; retains the higher sampling rate. |
| Rendered ECG page | Depends on dimensions, channels and compression | Supports an image-input study but introduces layout, rasterization and rendering choices. |

All 21,799 native 100-Hz signals would occupy approximately **0.975 GiB** as float32; training folds alone would occupy 0.779 GiB. At 500 Hz these estimates are 4.872 and 3.893 GiB. These are signal-array estimates only, excluding Python overhead, optimizer state and activations. WFDB returns float64 by default in the checked calls; a deliberate float32 conversion halves that signal-array memory. Reading records or small batches on demand avoids requiring a full cached cohort.

For a native waveform CNN–LSTM, time is an actual shared axis across the 12 leads: convolution can shorten the sequence before the LSTM. A 2D image CNN followed by an LSTM instead processes a sequence of spatial features; that ordering should not be called recovered physiological time unless the page layout and temporal relationship have been established. A waveform CNN–LSTM and an image CNN–LSTM answer different input-modality questions.

## Recommendation for this project

Keep the already frozen Mendeley LDA/CNN comparison intact. A CNN–LSTM using the same images and split can provide the requested controlled model comparison, with the existing label and sample-size limitations stated.

For a larger subsequent benchmark, PTB-XL is the more practical foundation. Use its native 100-Hz signals for an economical first temporal CNN–LSTM if waveform classification is the intended research task. If the intended deployed input is a paper ECG image, explicitly render a separate, versioned PTB-XL image cohort and train/evaluate an image model. Record ECG and patient IDs, official fold, SCP labels, source waveform hash, renderer version, all rendering parameters and random seeds, plus the final image hash. Start by inspecting a small development-only rendering sample before generating the full cohort.

Synthetic pages can support controlled experiments and pretraining, but clean synthetic test performance cannot demonstrate performance on real paper scans or phone photographs. Grid style, layout, cropping, print/scan artifacts and camera conditions can differ. Real-image evaluation requires a separately justified target dataset and compatible labels; the Mendeley four-folder results cannot simply be compared with a PTB-XL five-label score. Multiple synthetic variants increase image count without increasing independent patients.

This is a local feasibility and provenance assessment. The only new retained artifacts are this document and `data/audit/ptbxl_render_inventory.json`. No dataset switch, rendered cohort, model run or retrospective verification of manuscript performance was performed.

## Official source cross-check

The [PTB-XL v1.0.3 release](https://physionet.org/content/ptb-xl/1.0.3/) and [original dataset paper](https://www.nature.com/articles/s41597-020-0495-6) document the waveforms, annotations and recommended patient folds. Counts above come from the audited local v1.0.3 metadata rather than a historical abstract count.

The [PhysioNet Challenge 2024 documentation](https://moody-challenge.physionet.org/2024/) explicitly supports generating ECG images from PTB-XL waveforms using ECG-Image-Kit and evaluates on real scans/photographs. It also documents a separate acute/old MI derivation using PTB-XL+ 12SL labels. That is not evidence that our missing historical generator or its four-class mapping was valid. A full PTB-XL rendering experiment had not been executed at this assessment stage; subsequent generation and modeling are linked in the historical banner above.
